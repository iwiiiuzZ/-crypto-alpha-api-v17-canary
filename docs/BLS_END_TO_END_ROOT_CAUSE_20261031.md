# BLS接收成功但未消费的根因

2026-10-31北京时间13:43及13:45，独立网络使用主分支已有客户端标识与Atom/RSS格式兼容后，四个BLS官方URL的原文均成功读取并被认证后端接受。Worker直连403仍保留，不能把备用运输称作直连恢复。

严格跟踪发现，即使等待刷新，前台与扫描器仍只有八个非BLS来源成功。原先仅按“当前可用源”对账会通过，但不能证明BLS通过；新检查明确要求BLS CPI/PPI/就业/日历四源各自成功且批次被消费。

真实根因是存取契约不一致：认证接收端经scannerStatePut写入持久对象时保存`{value:{records},expiresAt}`，新闻消费者直接读取`records`，因此总是得到空备用集合。原隔离测试只用了未封装的KV路径，漏掉实际生产的持久对象路径。

修复限定为按原持久化契约读取value.records并检查expiresAt；每份原文仍须通过官方URL、哈希、格式及20分钟新鲜度校验。不会把备用来源当成最新突发消息、直接触发交易或改变八模型。

原生workerd测试已增加：真实接收函数→通用持久对象状态接口→封装落盘→新闻消费者→前台/扫描缓存相同批次；保持BLS直连403；过期封装必须拒绝。真实生产关闭还须等待R5f完整回归、受控发布、四源消费和十分钟严格窗口的新证据，R5e运行窗口通过不能替代本修复通过。
